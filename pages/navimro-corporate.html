서비스 기획서 · 법인 구매 경험 재설계

당시에는 법인고객 모바일 UI 디자인과 퍼블리싱에 참여했습니다. 지금은 그 화면을 바탕으로 사용자, 업무 순서, 예외 상황을 다시 정의하고 서비스 전체 방향을 기획했습니다. 아래 내용은 이번 포트폴리오에서 작성한 기획안입니다.

01 / 배경과 문제

기능 사이의 업무 연결

가입, 조직 관리, 승인, 결제, 증빙 화면은 각각 존재했습니다. 화면을 다시 살펴보며 한 건의 구매가 어떤 담당자를 거쳐 완료되는지 사용자 관점에서 연결할 필요를 발견했습니다.

02 / 기획 목표

내 역할과 다음 행동이 보이는 서비스

구매 요청자·승인자·결제자가 자신의 처리 건을 바로 찾고, 현재 상태와 다음 행동을 이해하며, 완료 후에는 주문과 증빙까지 확인하도록 설계합니다.

03 / 핵심 사용자

한 법인의 다섯 업무 역할

법인 마스터, 구매 요청자, 그룹 승인자, 결제자, 회계 담당자를 기준으로 진입 화면과 필요한 정보를 나눴습니다. 한 사람이 여러 역할을 맡을 수 있습니다.

04 / 설계 범위

가입부터 구매 이후 기록까지

법인 가입·초기설정, 구성원 승인, 구매신청, 승인, 결제와 구매 불가 예외, 주문·배송, 결제내역과 증빙, 조직·권한 관리를 하나의 서비스 범위로 묶었습니다.

PRINCIPLE 01

역할에 맞는 시작점

첫 화면에서 소속 법인과 내가 처리할 승인·결제·신청 업무를 먼저 보여줍니다.

PRINCIPLE 02

판단 근거와 상태를 함께

승인 상세에 요청 내용, 금액, 요청자, 승인 경로와 현재 단계를 함께 배치합니다.

PRINCIPLE 03

예외는 결제 전에 분리

구매할 수 없는 상품이 있으면 결제를 진행하지 않고 신청자 확인 경로로 보냅니다.

이 기획안의 완료 기준

  • 각 역할이 자신에게 필요한 처리 건과 다음 행동을 찾을 수 있다.
  • 한 구매 건의 신청·승인·결제 상태를 이어서 확인할 수 있다.
  • 완료된 주문에서 결제 기록과 증빙으로 이동할 수 있다.

실제 운영 정책 확인 필요

  • 승인 단계 수와 최종 승인 조건
  • 구매 한도, 결제 수단과 결제 권한
  • 구매 불가 상품의 취소·재신청 기준
  • 세금계산서 발행 단위와 시점
02 / SERVICE OVERVIEW

어떤 서비스인가

제가 작업했던 나비엠알오 법인고객 서비스는 기업의 구매 담당자가 조직 안에서 물품을 신청하고,
승인과 결제를 거쳐 구매 내역과 증빙을 확인하는 서비스입니다. 이번에는 각 담당자의 업무가 어디서 시작되고 이어지는지 다시 정리했습니다.

이용 시작

마스터 회원이 법인 정보를 등록하고 조직·그룹을 설정합니다. 발급된 법인코드로 구성원이 가입을 신청하며, 마스터 승인 화면이 이어집니다.

구매와 승인

구성원의 구매신청과 승인자의 검토가 분리되어 있습니다. 나의 승인내역, 법인 승인내역, 세부승인내역 화면에서 처리 상태를 확인할 수 있습니다.

결제와 기록

승인내역 결제, 주문·배송 조회, 월별 결제내역, 거래명세서, 세금계산서 조회 화면이 구매 이후 업무를 이어 줍니다.

제가 새로 정의한 기획 과제“구매 요청부터 승인, 결제, 증빙 확인까지 담당자별 업무가 끊기지 않도록 연결한다.”
03 / EVIDENCE & INTERPRETATION

기존 UI 작업에서 서비스 재기획까지

당시에는 전달받은 기획을 바탕으로 모바일 UI를 디자인하고 퍼블리싱했습니다.
이번 포트폴리오에서는 그 경험을 바탕으로 사용자 역할과 구매 흐름을 새롭게 기획했습니다.

당시 기존 작업

  • 법인 마이페이지와 승인내역 모바일 UI 디자인
  • 마스터·구성원 회원가입 화면 디자인 및 퍼블리싱
  • 조직·구성원 관리 화면 디자인 및 퍼블리싱
  • 승인내역 결제와 결제내역 화면 디자인 및 퍼블리싱
  • 거래명세서·세금계산서 조회 화면 디자인 및 퍼블리싱
  • 초기설정 팝업 UI 디자인 및 퍼블리싱

새롭게 재기획한 작업

  • 역할별 할 일을 마이페이지의 첫 화면에 모으기
  • 가입·구매·승인·결제·증빙을 하나의 흐름으로 설명하기
  • 승인 상세에서 요청 정보와 승인 경로를 함께 보여주기
  • 결제 전 구매 가능 상태와 예외 경로를 분명히 하기
  • 조직도 → 구성원 → 권한으로 이동하는 정보구조
  • 21개 최종 UI의 일관된 상태·용어·색상 체계
04 / USERS & PERMISSIONS

한 법인 안의 서로 다른 역할

기존 화면에 등장하는 마스터, 승인자, 결제자, 회계 담당자의 권한을 기준으로 업무 역할을 다시 정리했습니다. 한 사람이 여러 역할을 맡을 수 있다는 점도 화면 구조에 반영했습니다.

역할주요 업무필요한 화면·정보
마스터법인 가입, 초기설정, 구성원 가입 승인조직도, 구성원, 권한, 법인코드
구매 요청자상품 선택과 구매신청, 진행상태 확인내 신청, 승인 상태, 주문·배송
그룹 승인자구매신청의 내용과 금액 검토승인 대기 목록, 상세, 승인 경로
결제자승인된 건의 결제 처리결제 대상, 상품 상태, 결제 정보
회계 담당결제 기록과 증빙 확인월별 결제내역, 거래명세서, 세금계산서
05 / SERVICE FLOW

서비스 기획 플로우

가입은 마스터와 구성원 경로로 나누고, 구매 업무는 신청부터 승인·결제·조회까지 연결했습니다.
결제 전 구매할 수 없는 상품이 발견되는 경우에는 별도 확인 경로를 두었습니다.

기존 화면에 있던 기능을 연결해 제가 다시 설계한 흐름입니다. 승인 단계 수와 결제 조건은 실제 운영 정책을 확인한 뒤 확정해야 합니다.

DECISION 01역할부터 보이기

첫 화면에 소속 법인과 내게 필요한 승인·결제 업무를 요약합니다.

DECISION 02승인 판단 지원

요청 내용, 금액, 요청자, 현재 승인 단계를 한 화면에 놓습니다.

DECISION 03결제 전 예외 확인

구매 불가 상품은 바로 결제로 보내지 않고 신청자 확인 경로를 보여줍니다.

DECISION 04증빙까지 연결

월별 결제 기록에서 주문별 거래명세서를 찾고 세금계산서는 별도 조회합니다.

구매 상태 설계

신청 → 승인 대기 → 승인 완료 → 결제 요청 → 주문·배송 → 증빙 조회. 반려와 구매 불가 상품은 별도 상태로 분리했습니다.

예외 처리 설계

승인 반려는 요청자가 결과를 확인하도록, 구매 불가 상품은 결제자가 신청자에게 알리고 기다리는 흐름으로 표현했습니다.

운영 시 확인할 사항

승인 단계 수, 구매 한도, 승인자 부재, 결제 수단, 세금계산서 발행 기준은 실제 운영 정책에 맞춰 구체화해야 합니다.
